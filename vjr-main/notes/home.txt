###################
# WHAT IS A HOME? #
###################

The Home menu is a program ran on Core 1 of the ESP32. It is the other half of the BIOS, which also consists of
the background processes (see bios.txt for more).

Home is how users can load in games from the SD card onto their systems, as well as accessing system settings,
customization, test programs etc.

The Home button exists as a way to pause the current ROM running and access the Home menu.

When the Home menu is running, it acts like a normal program just like a game, except:

    - It is running on Core 1, not Core 2. This makes it not replace the current execution of the loaded ROM.
    - It does not communicate with the hardware through the BIOS API, but rather directly due to being in Core 1.
    - Allocates things into RAM for itself, and when a game is loaded/resumed, it releases them from RAM.



################
# HOME SIGNALS #
################

The Home menu runs on Core 1, so it does not use the BIOS API. Regardless, it will still use Signals
to interact with asynchronous hardware peripherals.

As mentioned in signals.txt, Display is different. Due to the synchronous nature of displaying, there is no Display
Channel. A Scene is still required to draw objects to the screen, which we run Scene::draw to display to.

But now, the nature of displaying is different across the ROM and the Home menu: the ROM uses the BIOS API 
function pointer, while the Home uses SPI directly.

To account for this, we will treat this with abstraction: suppose a generic DisplayBufferPusher that sends a 
Display Buffer to a Display. In Rust, this is equivalent to a trait. We can define a BiosPusher struct in the BIOS
code that inherits DisplayBufferPusher for interacting via SPI, and a RomPusher struct in the ROM code for interacting
via the BIOS API function pointer.

Getting the display to work correctly for the home menu and the ROM is very important.

Additionally, to ensure ownership and safe code, it may be that the ROM and Home need to keep two video buffers each.
This results in minimum 40 kB of RAM for video buffers, which is around 8% of the RAM (actually closer to 12% due to
DRAM being 320 kB). This is unfortunately a trade-off I will have to make.
